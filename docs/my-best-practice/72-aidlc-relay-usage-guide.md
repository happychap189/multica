## 72.1 这是什么

aidlc 接力是把一个需求从"一句话想法"推进到"可运营交付物"的人工接力流程：5 支小队按 phase 接力干活，每个 phase 结束由你做一次人审，通过后改派并 @ 下一队。队内派单、交付、互审、进度锚全部由 agents 自动完成；你只负责五类动作——**开工、看进度、人审、交接、终审**（全程 5 次人审，bugfix 路径 4 次）。

**读者假设**：导入已完成（1 个 skill + 14 个智能体 + 5 支小队就位）；会建 issue、写评论、用 @ 选择器、改派 issue 负责人。协议机制不在本文展开——方法论总览见包内 aidlc-relay-pack/SKILL.md，接力协议见包内 aidlc-relay-pack/relay-protocol.md。

## 72.2 你要打交道的对象

正常接力中，你只 @ 小队，从不直接 @ 智能体——队内派单由队长完成。你的五类动作对着三类对象：开工/人审/交接对着小队与 issue，看进度对着时间线，单点任务才直接对着智能体（见 72.4.2）。

## 72.3 全程走法（贯穿案例：会议决议追踪小工具）

案例：你要一个"会议决议追踪小工具"——把每次会议的决议、负责人与期限记下来并能查询。题材仅为代入用，任何需求都走同一套动作点。

场景设定：你是发起人，担任 P1 的**环节负责人**。环节负责人就是 issue 负责人（assignee）——人审与改派动作都以这个身份执行留痕。每个 phase 通过后可以把 assignee 改派给下一位同事；单人跑通时也可以全程自己担任。

时间线上你会遇到的称谓：**环节负责人**（issue 负责人，多数时间是你）、**队长**（小队的 leader 智能体，负责派单与发锚）、**worker**（被派单的成员智能体）、**reviewer**（队内评审角色，只审不产）。

走法总图：

```text
建 issue（todo）→ 指派自己 → @ P1 队 →（队内自动：派单/交付/互审/进度锚/交付摘要）
→ 人审 P1 → 改派 + @ P2 队 → 人审 P2 → … → 人审 P5
→ 改派 issue 给 P5 队 → 队长收尾 in_review → 你终审 done
```

### 72.3.1 开工

你的动作与小队的动作，按时间对齐：

| 时点 | 你做什么 | 小队做什么 |
|---|---|---|
| 开工 | 建 issue、指派自己、@ 队 | 队长读诉求描述，开始派单 |
| phase 进行中 | 等待、随时抽查时间线 | 派单 / 交付 / 互审 / 发进度锚 |
| phase 末 | 人审、改派、@ 下一队 | 发 phase 交付摘要后静默 |
| 终局 | 改派给 P5 队、终审置 done | 队长收尾 in_review |

**第一步：建 issue 并写清诉求描述。** 新建 issue（标题如"会议决议追踪小工具"），描述按下面骨架写——这是小队的唯一输入，写得越具体返工越少（可整段照抄后填空）：

```text
## 背景
<为什么需要这个工具，现状痛点>
## 目标
<做成什么样算成功，2-4 条，可验证>
## 范围
<要做的功能清单；部署形态（网页/服务）；用户是谁>
## 非目标
<明确不做什么，防止范围膨胀>
## 输入与输出
输入：<既有文档/代码库/参考资料；无则写"全新项目">
输出：<期望的交付形态，如"可访问的部署地址 + 源码 + 运维手册">
```

填好的示例（本案例）：

```text
## 背景
例会决议散落在各处纪要里，没有人跟进落实，重复讨论。
## 目标
决议可登记、可指派负责人与期限、可按状态查询；会前自动汇总上期未决项。
## 范围
网页工具；单工作区使用；覆盖登记/指派/查询与未决项汇总。
## 非目标
不做日历集成与移动端。
## 输入与输出
输入：全新项目，无既有代码库。
输出：可访问的部署地址 + 源码 + 基本运维手册。
```

**第二步：把 issue 指派给自己。** 打开 issue 详情页 → 负责人字段 → 选择你自己。这一步让"环节负责人"身份落位，人审留痕靠它。

**第三步：@ 一队开工。** 三步 @ 动作（本文唯一的 @ 教学动作，后面各节直接引用）：

1. 点开 issue 评论框，在框内输入 @——弹出提及选择器；
2. 输入队名关键词（如输入"启动"）过滤，点击列表中的 aidlc-阶段一-启动；
3. 评论框内出现带高亮的提及标记（这是真实提及的标志——纯文本队名不会唤醒小队，高亮标记消失或变成纯文字就删掉重插）。

确认插入后补齐正文（可照抄）：

```text
{此处为已插入的一队提及标记} 按 relay-protocol.md 跑 initialization。issue 保持 todo。
范围提示：<一两句话：本次项目形态（全新/改造既有系统）、验收形态、开工前必须知道的事>
```

**红线提醒**：issue 全程保持 todo，任何时候不要移入 backlog——进 backlog 的 issue 派单会被冻结，@ 队静默失效（中了怎么办见 72.5）。

标题与其他字段：标题写清"是什么"（如"会议决议追踪小工具"），不要只写"帮我做个工具"；标签、优先级按团队习惯设置，协议不依赖它们。

### 72.3.2 看懂进度：时间线上会出现什么

@ 出之后，issue 时间线就是接力的全部现场。你要能认出三种内容：

**进度锚**——每个 stage 完成后队长发的顶层评论，长这样（格式与计数以包内 aidlc-relay-pack/relay-protocol.md 为准）：

```text
[P1 2/3] workspace-detection done → next workspace-scaffold
```

读法：`[P1 2/3]` = 第 1 个 phase 的第 2/3 个 stage；`done` 前是该 stage 名，`next` 后是下一个。一个 phase 交完，锚的总数 = 该 phase 的 stage 数（P1 到 P5 依次为 3/7/9/7/7；bugfix 路径取裁剪后数量）。若看到锚末尾带修订标记（如 `(r2)`），说明该 stage 返工过一次。

读锚的三个异常信号：锚序号长时间停在同一格（对照每 phase stage 数判断是 stage 天然耗时还是停滞）；同一序号出现带修订标记的重复锚（该 stage 返工过，正常）；锚推进数量明显超出该 phase 的 stage 数（异常，联系运维）。

进度抽查节奏：第一次跑建议每次锚出现时都点开线程看一眼交付形态；熟练后每 phase 抽查 1-2 个线程即可。

**verdict 轮次**——reviewer 智能体对制品的评审结论，出现在派单线程内（点开锚之间的线程回复可见）：verdict 给出 READY/NOT-READY 结论与 findings 清单，并注明所读附件的修订号；制品返工后修订号递增（r1/r2…）。两类评审你只需知道区别：P2/P3 的评审是**参考式**（不阻塞推进，队长记录采纳情况）；P4 的评审是**对抗式**（未解决的问题会卡住 stage，同一 stage 返工上限 1 次——上限数值以包内协议为准）。

派单线程——锚与锚之间通常夹着若干派单线程：队长派单，成员在线程内交付（带制品附件与修订号），reviewer 在同一线程内给结论。你不必逐条读完，但抽查时点开看两件事：交付评论是否带附件与修订号；verdict 是否引用了所读附件的修订号。一个 reviewer 结论长这样（线程内示意）：

```text
verdict: READY。所读附件: intent-statement r1。
findings: 建议补充<某干系人>的角色定义（不阻塞）。
```

对抗式结论（P4）的示意：

```text
verdict: NOT-READY。所读附件: functional-spec r1。
findings: 逐条列出<编号 + 严重度 + 证据位置>；findings 未解决前，该 stage 不会被标记完成。
```

**phase 交付摘要**——一个 phase 干完后队长发的收尾评论（零提及），结构如下（格式以包内协议为准）：

```text
[phase 交付摘要] {小队名}
- 制品清单: <逐 stage 列出制品名 + 附件 + 修订号>
- reviewer verdicts: <各评审结论与队长采纳/回应；无 reviewer 的 phase 标注"无">
- 交接状态: <本队无残留任务>
```

看到交付摘要 = 这个 phase 干完了，该你人审了（下一节）。摘要之后时间线会安静下来——这是正常的，小队在等你。

一个 phase 在时间线上的完整样子（P1 示例）：

```text
（你的 @ 队评论）
[P1 1/3] state-init done → next workspace-detection
[P1 2/3] workspace-detection done → next workspace-scaffold
[P1 3/3] workspace-scaffold done → next phase-summary
[phase 交付摘要] aidlc-阶段一-启动
- 制品清单: aidlc-state / 探测结论 / 制品空间说明（各带附件与修订号）
- reviewer verdicts: 无
- 交接状态: 无残留任务
（时间线安静——该你人审了）
```

### 72.3.3 人审（每个 phase 一次）

**审什么**：按包内 aidlc-relay-pack/relay-protocol.md 第 4 节对应 phase 的清单一项项核对，四段固定：核心制品齐不齐、reviewer 结论有没有记录、附件修订号对不对、本队有没有残留任务。你不必读全部制品，但至少要抽查：目标/范围类制品与你的诉求描述是否一致、测试结果类制品是否真实（有测试数据而非"已完成"三个字）。

五个 phase 的人审速览（细节以包内 aidlc-relay-pack/relay-protocol.md 第 4 节为准）：

| phase | 锚计数 | reviewer verdicts 栏预期 | 人审重点一句话 |
|---|---|---|---|
| P1 | 3 | 标注"无" | 探测结论与制品空间齐备，项目基线立住 |
| P2 | 7 | 2 条参考式结论 | 范围与非目标守住你的诉求，意向清单覆盖目标 |
| P3 | 9 | 6 条参考式结论 | 需求/故事与目标一致，工作单元拆分到可开工 |
| P4 | 7 | 4 条对抗式结论（含返工轮次） | 代码与测试结果真实，未决问题逐条裁决 |
| P5 | 7 | 标注"无" | 部署与验证证据真实，确认进入终局两段式 |

**通过**——发一条核对结论评论（可照抄）：

```text
[人审结论] P{n} 通过。
核对项：<制品逐一核对情况 + 修订号 + verdict 栏与 phase 实际一致 + 无任务残留>
交接声明：改派 <下一环节负责人>，@ <下一支小队> 启动 <下一 phase 名>。
```

然后执行 72.3.4 的两步交接。

人审是接力的唯一推进节拍：交付摘要发出后小队会一直安静地等你，不会催审——拖审在时间线上的表现与停滞相同，别让 issue 歇在你的收件箱里。

**打回**——发一条带修改要求的评论（可照抄）：

```text
[人审结论] P{n} 打回。
问题：<逐条列出，点名制品与修订号>
要求：<逐项修改要求 + 完成判定标准>
重审入口：完成后 @ 本队小队续跑并重发交付摘要。
```

写"重审入口"这行时，在句末用 72.3.1 的三步 @ 动作插入本队提及标记（不是纯文本队名），发送后小队即重新开工。

**打回后会发生什么**：受影响的 stage 按契约返工，制品修订号递增，时间线上出现带修订标记的新锚（如 `[P3 5/9] reverse-engineering done (r2) → next refined-mockups`），完成后重发交付摘要。返工轮次的规则与上限数值以包内 aidlc-relay-pack/relay-protocol.md 为准。你再审一轮即可。

打回的粒度由你掌握：只点名有问题的制品，未点名的 stage 不会返工。人审投入的建议：产出抽查 + 清单四段即可，不必逐字读全部制品；但发现目标偏离或证据不实时宁可打回一轮——问题带病交接给下游 phase 只会被放大。

### 72.3.4 交接：通过后的两步动作

人审通过后，**两步缺一不可**：

1. **改派**：issue 详情页 → 负责人字段 → 搜索并选择下一 phase 的环节负责人 → 保存。单人跑通时改派给自己也行，但建议仍然真实执行改派动作——人审留痕的完整性靠它。
2. **@ 下一队**：按 72.3.1 的三步 @ 动作插入下一支小队的提及标记，正文可照抄：

```text
{此处为已插入的下一队提及标记} 按 relay-protocol.md 跑 <下一 phase 名>。issue 保持 todo。
范围提示：<本 phase 需要强调的范围要点；上一 phase 结论有侧重时在此点名制品名>
```

为什么是两步：**改派是留痕**——人审通过的证据就是"核对评论 + 负责人变更时间线"，缺了它这轮人审在时间线上不存在；**@ 是触发**——不 @ 下一队，下一队队长不会被唤醒，接力停在这里。只做其一都会断链。

### 72.3.5 终局：最后一步永远是人

P5 人审通过后，进入两段式收尾：

1. **你把 issue 改派给 aidlc-阶段五-运营**（负责人字段直接选小队——全程唯一一次 assignee 是小队）。这个改派动作就是授权：它允许 P5 队长收尾这个 issue。
2. **队长把 issue 收尾到 in_review**，并发一条收尾评论（"接力完成，提交人审"）。这是队长全程唯一一次动 issue 状态。
3. **你终审置 done**。打开 issue → 状态字段 → 置为 done。

置 done 前多看一眼：P5 的人审除常规四段外，重点确认部署日志、冒烟测试与健康检查三件证据真实存在——这是关单前的最后防线。

为什么最后一步留给人：协议把 `done` 设计为人类的终审签收——agents 无权关单，队长的授权边界止于 in_review。收尾语义以包内 aidlc-relay-pack/relay-protocol.md 为准。置 done 后小队静默，本轮接力结束，制品都在制品空间目录里。

如果 P5 人审发现问题：同 72.3.3 打回，P5 队返工后重走"交付摘要 → 人审 → 两段式"，两段式动作每次都要重新走一遍。

## 72.4 场景索引与局部用法

### 72.4.1 场景 → 章节索引（首次照走后的日常直达）

| 场景 | 直达 |
|---|---|
| 带一个想法开工 | 72.3.1 |
| 看进度/读时间线 | 72.3.2 |
| 每 phase 人审（通过/打回模板） | 72.3.3 |
| phase 通过后交接 | 72.3.4 |
| 终审关单 | 72.3.5 |
| 接力停滞自救 | 72.5 |
| 只需单个智能体干一件小事 | 72.4.2 |
| 只要某个 phase 的产出 | 72.4.3 |
| 缺陷修复快路径 | 72.4.4 |

索引覆盖首次照走之后的日常复用；第一次仍建议通读 72.3。

### 72.4.2 单独 @ 某个智能体做一次性任务

适合没有完整接力、只要一件产出的场景。优先选这些角色：aidlc-product-lead / aidlc-architecture-reviewer（评审一份需求或设计文档）、aidlc-design（一版线框）、aidlc-developer（一份代码库扫描报告）、aidlc-composer（工作流裁剪提案）、aidlc-compliance / aidlc-devsecops（合规/安全横切校验）。

操作：建一个 issue（保持 todo）→ 按 72.3.1 的三步 @ 动作，第 2 步输入的是智能体名字而非队名 → 正文可照抄：

```text
{此处为已插入的目标智能体提及标记} 请完成一次单独任务。
目标：<一句话>
输入：<材料清单，材料挂在本 issue 附件>
期望产出：<制品名与形态>
交付方式：完成后回复本评论。
```

这不是接力流程，没有锚与交付摘要；智能体回复后你自己核对并关单。单点任务单独建 issue，不要复用正在跑接力的 issue——避免污染接力时间线。

### 72.4.3 只启用某个 phase 队

只要某个 phase 的产出，不要完整接力——例如只要 P2 的范围文档与意向清单，或只要 P3 的需求、故事与领域设计。开工动作与 72.3.1 完全相同，只是第三步 @ 的是目标小队，范围提示里写明"只跑本 phase，交付摘要后停止"。交付摘要后照常人审；通过后**不再改派**——你直接把 issue 置 done（你就是终审者，语义同 72.3.5）。进度锚计数 = 该 phase 的 stage 数（数值以包内协议为准）。

### 72.4.4 bugfix-9 快路径

**何时用**：同时满足三条——已知的缺陷/回归修复（不是新需求）；需求上下文已由原运行制品或既有文档承载（无需重跑构思与全量分析）；修复范围落在"代码修复 → 构建测试 → 部署验证"通道内。反例：根因涉及需求理解错误、需要需求层返工的，走完整接力在 P3 人审打回，不用本路径。

**入口**：开工动作同 72.3.1，第三步 @ 一队时正文说明走 bugfix 路径（可照抄）：

```text
{此处为已插入的一队提及标记} 按 relay-protocol.md 跑 bugfix 路径。issue 保持 todo。
范围提示：<缺陷现象与复现步骤、根因范围线索、目标环境；需求上下文出处>
```

**与完整接力的区别**：只跑 9 个 stage（P1 全部 + P3 两个 + P4 两个 + P5 两个），4 次人审（P1/P3/P4/P5，P2 整队跳过）；进度锚计数取每 phase 本次运行的 stage 数；终局两段式与完整接力完全相同。路径构成与逐 stage 说明见包内 aidlc-relay-pack/bugfix-relay-path.md（数值以协议为准）。

与完整接力相同的部分：协议、锚格式、人审动作、终局两段式全部照旧——本文 72.3 的全部动作点直接适用，只是 phase 序列变短（P1 → P3 → P4 → P5）。4 次人审的核对范围按本次运行的 stage 裁剪（如 P3 只核两件制品），清单结构与动作不变。bugfix 路径的锚长这样（计数以协议为准）：

```text
[P3 1/2] requirements-analysis done → next reverse-engineering
```

## 72.5 常见卡住与自救

**判断停滞**：日常用**臂 1 的代理判据**——无新评论约 30 分钟且无进行中任务。满足即按下面步骤自救。完整的三臂判据见包内 aidlc-relay-pack/relay-protocol.md 第 5 节（分钟数等数值以协议为准）；若任务长时间停在排队未被认领，多半是运行时离线，先恢复运行时再走下面步骤。判据出现后尽快处理（当天内）；停滞不会自愈，拖得越久制品间的断层越多。

症状速查：

| 症状 | 最可能原因 | 处理 |
|---|---|---|
| @ 队后时间线毫无反应 | issue 在 backlog，或提及是纯文本 | 移回 todo；按三步 @ 重插提及 |
| 干到一半停了（无新评论且无任务在跑） | worker 交付漏 @ 队长 | 按下面四步自救 |
| 任务长时间停在排队无人认领 | 运行时离线 | 先恢复运行时，再走自救步骤 |
| 锚在涨但交付摘要迟迟不来 | 正常（phase 还没干完） | 继续等，别干预 |

**自救步骤**（按序执行）：

1. **先读最后一条进度锚**（重入护栏）：锚之后若时间线仍有新活动或任务在跑，唯一正确动作是**等待**——不要 @、不要改派。
2. **查最后一条交付评论**：点开线程，若交付回复在线程内但没有 @ 队长，这就是停滞最常见的原因——在该线程内补一条回复，按三步 @ 动作插入**队长**的提及标记，正文写"请按恢复协议从最后一条进度锚续跑"。
3. **补 @ 仍无效时走主路径**：重新 @ 队长所在的小队（同 72.3.1 的三步 @），正文"按恢复协议续跑"。队长被唤醒后的行为是恢复续跑而非重派，你等锚续发即可，不要自己重派或重复 @ 多次。
4. **登记**：每次恢复（含确认是虚惊的）记一行到你的制品目录（建议文件名 aidlc-relay-recovery-log.md，格式以包内协议为准）：

```text
时间 | 触发臂 | 最后一条进度锚 | 现象描述 | 干预动作 | 恢复结果
```

恢复动作发出后，等几分钟确认时间线出现新评论或锚续发，即已接上；仍无反应就重复第 2 步，并联系运维同学——他们手里的检查清单见仓库内 docs/my-best-practice/71-aidlc-relay-playbook.md。

**verdict 反复打回怎么办**：P4 对抗式评审同一 stage 返工上限 1 次；达上限仍有未解决问题时，队长会在交付摘要如实列出——这时裁决权在你：接受（风险自担，在核对评论里写明）或打回（按 72.3.3 打回模板）。人审层面的打回没有协议上限，但同一问题打回两轮仍无改善，建议先线下对齐诉求再续跑，避免无限返工循环。

**issue 误入 backlog**：症状是 @ 队评论发出后时间线毫无反应——无派单线程、无锚。先检查 issue 是否被移进了 backlog 分类：backlog 中的 issue 派单被冻结，这是静默断链的头号原因。处理：把 issue 移回 todo → 重新按 72.3.1 的三步 @ 动作 @ 队 → 确认派单线程出现。预防：接力的 issue 不要卷入任何批量归类或看板整理操作。

**什么时候找运维**：自救两轮仍无反应、锚计数明显异常、任务长时间排队（运行时离线形态）——这三种情况把 issue 链接与最后一条进度锚发给运维同学，他们的检查清单与工具见仓库内 docs/my-best-practice/71-aidlc-relay-playbook.md。

## 72.6 照走自检清单

逐条打勾；任何一条不满足，回到对应小节处理后再继续。

**开工前**：

- [ ] issue 已建为 todo（不是 backlog），诉求描述含背景/目标/范围/非目标/输入与输出五段
- [ ] issue 负责人已指派给自己
- [ ] @ 队评论用的是选择器插入的提及标记（有高亮，不是纯文本队名）
- [ ] 已想清楚本次走完整接力还是 bugfix 快路径，并在正文说明

**进行中（每个 phase 人审时）**：

- [ ] 锚计数 = 该 phase 的 stage 数（返工锚带修订标记，可解释差额）
- [ ] 制品附件都有修订号；评审结论（若有）引用了所读附件与修订号
- [ ] 交付摘要的 reviewer verdicts 栏与该 phase 实际相符（无 reviewer 的 phase 标"无"）
- [ ] 交付摘要之后时间线安静，无本队残留任务迹象
- [ ] 交付摘要出现后尽快人审——拖审是接力的隐形停顿
- [ ] 通过：已改派负责人 + 已 @ 下一队（两步都做了）
- [ ] 打回：问题、要求、重审入口三要素齐了，且重审入口里插入了本队提及标记

**终局**：

- [ ] P5 人审通过后已把 issue 改派给 P5 小队
- [ ] P5 三件部署证据（部署日志/冒烟结果/健康检查）已点开确认真实存在
- [ ] 队长已收尾到 in_review 并发收尾评论
- [ ] 你已亲自把 issue 置 done（agents 无权替你关单）
- [ ] 恢复事件（若发生过）已登记并保存到制品目录
